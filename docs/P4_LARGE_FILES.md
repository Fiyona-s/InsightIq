# Large files, speed and reliability (PRODUCT-POLISH P4)

All timings are from this build on a development laptop (Apple silicon, one CPU used by the app) with a **synthetic, fictional** orders file (8 columns, fixed seed) generated by `backend/scripts/make_synthetic_csv.py`. It is never committed (`*.csv` is ignored; only the listed fictional demo files are allowed). No live AI was used: questions went through the controlled test provider and the real query guard and sandbox.

## The upload limit, and what the 2 GB container really allows

`MAX_UPLOAD_MB` and `MAX_UPLOAD_ROWS` (environment) set the limits. The shipped defaults are the **measured safe values for the 2 GB / 1 CPU container**: **60 MB and 1,000,000 rows**. The upload is streamed to disk in 1 MB pieces and checked row by row in constant memory; the file is never held whole in memory by the upload path. A body above the limit is cut off while it arrives, with a plain message.

| File | Where | Result |
|---|---|---|
| 500,000 rows, 28 MB | container, 2 GB, 1 CPU | added in 68 s, memory sampled at about 0.5 GiB, no problem |
| 1,000,000 rows, 53 MB | container, 2 GB, 1 CPU | added in 131 s, memory sampled at about 0.95 GiB |
| **1,800,000 rows, 97 MB (about 100 MB)** | container, 2 GB, 1 CPU | **failed after 202 s with a plain "Operation failed" error** at about 1.6 GiB; the app stayed up and left nothing behind |

So **100 MB does not hold under 2 GB today**, and the default is not 100 MB. The reason is outside this stage's files: when a file is added, the dataset editor (`dataset_editor.py`, byte-identical by Rule 3) reads every row into memory, and the revision step reads them again. About 100 seconds of the time for 500,000 rows used to be spent there. Raising the limit safely needs either more memory for the container or a change to those two files, which needs your approval first. Memory samples were taken every 4 seconds, so short peaks can be higher than shown.

Proxies: the front-end image allows bodies up to 110 MB and streams uploads without buffering; the hosted proxy file does the same (`max_size 110MB`). The app's own limit is what applies.

## Timings on the 500,000-row synthetic file (the budget test)

| Step | Measured | Budget (the test fails above it) |
|---|---|---|
| Upload to ready | 29 s | 120 s |
| Column profile | 2.5 s | 10 s |
| Median question (5 different questions) | 1.7 s | 6 s |

Before this stage each question on that file took about 10.7 s, because the full-column profile and a hash of the whole dataset file were recomputed for every question. They are now kept per file state (size and modification time of the data file and its write-ahead log) and recomputed only when the file changes; the edit and revision tests still pass, which proves an edited file is re-read. The first upload was also slow (7 minutes) because rows were inserted one statement at a time; the fast loader reads the checked file with DuckDB's own reader and falls back to the exact row-by-row path if anything disagrees.

## What an owner sees

- A progress bar while the file uploads, then "Reading and checking your file…", then after 6 seconds "Still working. Large files can take a minute or two."
- Plain messages above the limit: "That file is too big (the limit is N MB)…" and for too many rows.
- Column checks say "Still checking your columns. Large files take longer." after 6 seconds.
- Preview pages 25 rows at a time (the server serves one page, up to its row limit); question results are limited to 1,000 rows, shown 10 first with "Show all".
- Cancel is the existing "Cancel run" on a running question; failed questions have "Retry"; a crashing page is caught by an error boundary with "Try again" and the rest of the app keeps working.
